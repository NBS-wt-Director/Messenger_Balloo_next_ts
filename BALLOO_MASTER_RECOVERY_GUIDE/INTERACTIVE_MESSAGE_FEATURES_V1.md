## 2. ПЕРЕСЫЛКА СООБЩЕНИЙ (FORWARD)

### 2.1 Описание

**ID:** MESG-019 (расширение)  
**Тип:** `chat`  
**Класс:** `feature`  
**Premium:** ❌ Free

**Описание:** Пересылка сообщений из одного чата в другой с сохранением авторства.

### 2.2 Ограничения

| Параметр | Значение |
|----------|----------|
| **Макс. чатов за раз** | 5 |
| **Secret Chats** | ❌ Запрещено (E2E) |
| **Сохранение автора** | ✅ Всегда |
| **Редактирование перед отправкой** | ✅ Опционально |

### 2.3 UI/UX

**Пользовательский поток:**
```
1. Долгое нажатие на сообщение
   ↓
2. Контекстное меню → "Переслать"
   ↓
3. Выбор чатов (до 5)
   ↓
4. Опционально: добавить комментарий
   ↓
5. Отправить
```

**Отображение в чате:**
```
┌────────────────────────────────────┐
│ ↪️ Переслано от Алексей Иванов    │
│                                    │
│ Привет! Как дела?                 │
│                                    │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  │
│ 👁️ Просмотры: 12                  │
└────────────────────────────────────┘
```

### 2.4 API

```typescript
// Пересылка
POST /api/v1/messages/:id/forward
{
  "chat_ids": ["uuid1", "uuid2"],  // до 5
  "comment": string?,               // опционально
  "hide_sender": boolean?           // только для групп (admin)
}

// Ответ
{
  "success": true,
  "forwarded_to": ["uuid1", "uuid2"],
  "message_ids": ["new_uuid1", "new_uuid2"]
}
```

### 2.5 База Данных

```sql
messages: {
  forward_from_id: UUID REFERENCES messages(id),
  forward_from_sender: UUID REFERENCES users(id),
  forward_from_chat: UUID REFERENCES chats(id),
  forward_count: INTEGER DEFAULT 0,
  forwarded_at: TIMESTAMP
}
```

### 2.6 События WebSocket

```javascript
// Отправитель
socket.emit('message:forward', {
  message_id: 'uuid',
  chat_ids: ['uuid1', 'uuid2']
});

// Получатели
socket.on('message:new', {
  ...message,
  is_forwarded: true,
  forward_from: { ... }
});
```

### 5.5 База Данных

```sql
CREATE TABLE scheduled_messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  chat_id UUID NOT NULL REFERENCES chats(id),
  sender_id UUID NOT NULL REFERENCES users(id),
  
  content TEXT NOT NULL,
  type VARCHAR(50) DEFAULT 'text',
  attachment_id UUID,
  
  scheduled_at TIMESTAMP NOT NULL,
  status VARCHAR(20) DEFAULT 'pending',  -- pending, sent, failed, cancelled
  
  sent_at TIMESTAMP,
  error_message TEXT,
  
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_scheduled_messages_scheduled_at ON scheduled_messages(scheduled_at);
CREATE INDEX idx_scheduled_messages_status ON scheduled_messages(status);
```

### 5.6 Cron Job (Отправщик)

```javascript
// Запускается каждую минуту
async function sendScheduledMessages() {
  const now = new Date();
  
  const messages = await db.query(`
    SELECT * FROM scheduled_messages
    WHERE status = 'pending'
      AND scheduled_at <= NOW()
  `);
  
  for (const msg of messages) {
    try {
      // Отправка сообщения
      await sendMessage(msg.chat_id, msg.sender_id, {
        content: msg.content,
        type: msg.type,
        attachment_id: msg.attachment_id
      });
      
      // Обновление статуса
      await db.query(`
        UPDATE scheduled_messages
        SET status = 'sent', sent_at = NOW()
        WHERE id = $1
      `, [msg.id]);
      
    } catch (error) {
      await db.query(`
        UPDATE scheduled_messages
        SET status = 'failed', error_message = $2
        WHERE id = $1
      `, [msg.id, error.message]);
    }
  }
}
```

```sql
CREATE TABLE message_templates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  forward_from_sender UUID REFERENCES users(id),
  forward_from_chat UUID REFERENCES chats(id),
  forward_count INTEGER DEFAULT 0,
  
  -- Редактирование
  is_edited BOOLEAN DEFAULT FALSE,

  is_deleted BOOLEAN DEFAULT FALSE,

  deleted_by UUID REFERENCES users(id),

  -- Временные метки
  sent_at TIMESTAMP DEFAULT NOW(),
  delivered_at TIMESTAMP,

  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()

### ВОПРОС 1: Отложенные сообщения — Push-уведомление об отправке?

**Влияние:** UX (15%), Performance (5%)

**Контекст:** Когда отложенное сообщение фактически отправляется (в заданное время), нужно ли отправлять push-уведомление отправителю?

#### Вариант 1.1: ✅ Отправлять всегда
```
Сообщение отправлено → Push: "Ваше сообщение отправлено в чат 'Рабочая группа'"
```

**Сильные стороны:**
- Пользователь уверен что сообщение ушло
- Удобно для важных сообщений (поздравления, напоминания)
- Снижает тревожность "а вдруг не отправилось?"

**Слабые стороны:**
- Дополнительная нагрузка на push-сервис (до 5 сообщений/день на пользователя)
- Может раздражать при частом использовании
- Дополнительный API call к Firebase/Yandex Push

**Почему именно этот вариант:** Рекомендуется для **Premium** пользователей, опционально для Free.

---

#### Вариант 1.2: ❌ Не отправлять никогда
```
Сообщение отправлено → Без уведомления
```

**Сильные стороны:**
- Нет дополнительной нагрузки
- Нет риска spam-уведомлений
- Проще реализация

**Слабые стороны:**
- Пользователь не уверен в отправке
- Нужно заходить в приложение чтобы проверить
- Может снизить доверие к функции

**Почему именно этот вариант:** Подходит для **MVP** чтобы упростить запуск.

---

#### Вариант 1.3: ⚙️ Только если пользователь офлайн в момент отправки
```
if (user离线 at scheduled_time) → send push
else → no push
```

**Сильные стороны:**
- Баланс между информированием и спамом
- Логично: если онлайн — увидит сам
- Экономия ресурсов

**Слабые стороны:**
- Сложнее реализация (нужно проверять online статус)
- Требует WebSocket интеграции

**Почему именно этот вариант:** **Оптимальный выбор** для V1.

---

#### Вариант 1.4: 🔧 Настройка в настройках
```
Настройки → Уведомления → ☑ "Отложенные сообщения"
```

**Сильные стороны:**
- Полный контроль у пользователя
- Гибкость
- Снижает негатив от нежелательных уведомлений

**Слабые стороны:**
- Сложнее UI (ещё одна настройка)
- Пользователи могут не найти
- Нужно хранить состояние в БД

**Почему именно этот вариант:** Рекомендуется для **V2**, не для V1.

---

### ВОПРОС 2: Отложенные сообщения — Отдельный виджет в главном меню?

**Влияние:** UX (20%), Completeness (10%)

- Не видно общую картину
- Сложно управлять всеми запланированными

**Почему именно этот вариант:** Подходит для **MVP**.

#### Вариант 2.2: ✅ Отдельная страница в меню

**Сильные стороны:**

### ВОПРОС 3: Шаблоны — Общие или привязанные к группам?

- Админы не могут создать шаблон для конкретной группы
- Ограничивает сценарии использования

**Почему именно этот вариант:** Подходит для **базовой версии**.

- Максимальная гибкость
- Админы могут создавать шаблоны для своей группы

**Слабые стороны:**

- Нужно проверять права доступа

**Почему именно этот вариант:** **Рекомендуется для V1** — критично для админов групп.

#### Вариант 3.3: ❌ Только групповые
```

**Слабые стороны:**
- Бесполезно для личных чатов
- Ограничивает сценарии
- Не подходит для поддержки

**Почему именно этот вариант:** **Не рекомендуется**.
